"Cybernetica" or "Cybernetes"

This is a sample of a prototype IDE (non functional, graphicwise.) that we have discussed sporadically in past discussions, GPT. 

What's fascinating about this IDE (not essentially an IDE...the taxonomy is termporary...) is that it would not essentially replace the text source code, nor would it break any pre-existing IDE developer workflows. This would act as a kind of "exoocular apparatus"; an abstraction of the underlying source code, rendered as graphical interpretation.

The main idea is the graphics themselves are controlled via a query-language; suggesting a third emergence; queryable source code. This may open the problem of unecessarily analytical source code... however, I suspect the query itself will eventually be memorized and integrated, just as any source language, as a kind of "membrane" between the source and the graphic. Establishing a Cybernetic relata; such that the graphics are semantially tuned by the programmer, while the pragmatics of the system emerges as a consequence.

For the otherwise, topologically-ambigious source underneath, this would not only dramatically increase visibility; it would potentially provide new ways of looking at software problems. Diagnosis, Analytics, Performance, Lifecycles, etc. All of this is quite ambitious, so to concretize the idea, the program itself is simply; Reading source code, and translating it into multiple views. Those views are controllable via a query microgrammar (as mentioned previously.)

While these views may someday be interactive, the primary idea is in Unifying the necessity of spatial-locomotive-orientational mapping of Human-Neurology -and- the control and precision of source code. Precision without vision, will 

This program also actively explores Representational-and-Tangibility problems, which is an ongoing research effort in my local work. We assume the majority of software issues today, have unforseen consequences. A programmer/engineer authors code in real-time, while having little to no tactile awareness of the structures emerging underneath the source code. It would be as if an electrical engineer was forced to operate at an incorrect representational level for the task; i.e., crunching math calculations instead of manipulating the wiring directly. While the math would surely be precise, and it would theoretically result in the same precision as hand-on engineering; in It would almost always lead to catastrophic visibility issues. 

That is primarily the metaphor we are basing for this project; source is not a thinking, analysis nor engineering layer for Human-beings; it is the level of instruction. It is insufficient for architecture, structure and reasoning.

What's fascinating about source code, is often the "source" of things are not visible. For example, the most common class of bug is typographic; not topological! "Bug-hunting" is an inevitable part of the process, but we suggest the representation of source, is an unjustified burden to the finite Cognitive resources of the Human engineer.

This also suggests the strongest aspect of the mechanics; whereas UMLs and various Schematics have been attempted to aid in these highly problematic source issues; these are largely artifacts. They do not execute alongisde code, nor do they update with the code. This prototype however, addresses this issue by explicitly executing a copy of the source code (simply running on a localhost server, for example), and providing real-time data of exactly the same data being processed at the underlying source. If this prototype is to justify it's complexity, this is the key area I believe; automated graphics of real-time code processing.

Another idea is the grammar aspect of the code; what if the visual was translated in such a way, that the code speaks for itself, rather than requiring mass annotation like documentation? This suggests the categorial power of "view types"; assuming one is diagnosing a cyber-system; entering a "diagnosis" panel, appears to afford semantic views of otherwise, ambigious source.

There are also plenty of other ideas, such as "Domain separation" where program types (not merely data-types) are separated into class-distinctions. Logic, Math, Networking etc.

This also emerges a new term; Software is largely an idea of the past. An operating system is Software; a computer program is not merely software; it may be "Cyberware"; something closer to "An executable machine within in the computer, with it's very own bespoke enviornment." 

This suggests a new terminology for the coming age of AI-dominant technology; Cyberneerring; Where the Human-being is no longer responsible for merely the authoring or writing of source code; but the Ethics, Architecture, Standardization, Sustainability, Reliability, Visibility, Transportability, Communicability and Diagnosibility of Computer programs. This is what we call the "Cyberethos"

"Cybernete", "Cyberware", "Cyberneering", "Cyberethos" and "Cybernetica" as some taxonomies of this project.

The most challening aspect of this project is scaling complexity; an AST can easily parse source code, and node can walk through the file tree... the hardest part is in unifying the ideas proposed in this Thesis, into an actual working product, and even more challenging; build the product so that it does not get in the way of building programs.
