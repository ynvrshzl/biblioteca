## Applications in Programming (Principia Cybernetica)

If programming languages would eventually (invariantly/inevitably) evolve into higher level "asset interfaces"... i think technology today would be far more robust and maintainable into the future... (however, that is a thread for another discussion)

**Why aren't templates emphasized enough in software today?**

For example, implementing basic sort algorithms (computer-science), pan-zoom (gui), and basic search engines (which would impelment lower-lever primitive templates...) are all common systems... and yet, we are often re-creating them. The strangest part of this phenomenon; is how other areas of software technology have already implementing "shared source" (github/npm packages distribution and versioning, for example) and "template" systems (github templates, code snippets, even boilerplate)

This is beyond boilerplate however; what if the language itself was constructed entirely from templates, rather than the "micro-instruction" presupposition of source. If we compare-and-constrast our extensive history analysis and research in this area... I am not surprised if this fundamental change of the substrate, would influence every aspect of authoring software today.

Templates, Blueprints, Prototypes and Assets are interesting objects of abstraction; these are not merely reuseable pieces of logic; they are distributions of space (code, source, logic, etc.) and affordances of time (

In some sense, a template fundamentally affords two Domains:

- Space-encoded Memory: The reuse of prior or specified structures, without re-implementation (which is essentially, a kind of "static" memory; where instead of rebuilding every time, we begin from a previously constructed point.)
    
- Grammar and Principle of Distribution: Eventually, systems become so complex, that the search space exhausts our Human resources (this is true even for machine implementations of algorithms, for example.) A template system acts as a kind of "membrane" between system and expression; which is essentially how hierarchical systems (like grammar) are constructed.
    

In some fundamental sense, the Engineer today is already implementing these systems in computer software (sometimes, even as DSLs.) That is one of the primary motivations for this project (which is currently undefined, but the conceptual scaffolding is outlined in this introductory proposition.)

This suggests not only templates serving as a mechanic for saving time and establishing standards-as-source (this is really important)... but the templates-building-templates would afford a kind of architectural shape-language that has alreaddy been emphasized

I think assets/templates/prototypes/blueprints (aliases for the same concept of re-useable source) is one of the major problems in the life of a Software-Engineer today... Domain separation is also incredibly important becuase it's essentially the "Category Theory" of how different systems interact in code (which again, is something mostly ambigious when authoring source code systems; the engineer relies on two fundamental strategies to infer the missing tangibility; mental-maps of the code, and output referencing.)

These afford distinct domains of software, which are otherwise ambigiously collapsed into the same shared substrate (plaintext source). (this is also a discussion for another day.)

Sample:

Rather than a micro definition of instructions, i.e., `function x(a, b){ return a + b }` ...We instead opearte at a level above the micro instruction; at composition and definition: `Language.ops.add(a, b)` ... which itself is a composition; inspectable and decomposable: (a kind of micro-template grammar): `new Composition(add).namespace(add).class(transformer).recievers(a, b).out(return).def(a + b).sign(1)`

The linguistic types... e.g., `type: transformer`, `TYPEOUT: RETURN`, `RECIEVERS: A, B` and `CALCULANT: +`

Very similar to Compiler AST's
